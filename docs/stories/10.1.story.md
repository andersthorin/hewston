# Story 10.1 — Core Nautilus Engine Integration

**Story ID**: S10.1  
**Epic ID**: E10  
**Status**: Ready

## User Story
As a **trading strategy developer**,  
I want **real Nautilus Trader backtesting execution instead of the current stub implementation**,  
So that **I can get accurate, professional-grade backtesting results with proper execution simulation**.

## Context
First story of Epic 10. Focus on replacing the stub Nautilus adapter with real Nautilus Trader engine while maintaining exact interface compatibility. This is the foundation for enhanced strategy support and metrics.

## Dependencies
- **Depends on**: Epic 4 (existing BacktestRunnerPort interface and artifact structure)
- **Blocks**: S10.2 (Strategy Framework), S10.3 (Enhanced Metrics)

## Acceptance Criteria

### Functional Requirements
**AC1**: Replace stub SMA crossover calculations with real Nautilus Trader engine execution
- **Given** a backtest request with SMA crossover strategy
- **When** the backtest is executed
- **Then** Nautilus Trader engine performs the execution (not Polars calculations)
- **And** results are equivalent to or better than stub implementation

**AC2**: Maintain exact same input/output interface as current BacktestRunnerPort
- **Given** existing backtest job execution (`make backtest` command)
- **When** the new Nautilus engine is used
- **Then** all input parameters work unchanged (dataset_id, strategy_id, params, seed)
- **And** output format matches existing artifact structure

**AC3**: Convert 1m Parquet bars to Nautilus-compatible data feed format
- **Given** existing 1m bars in Parquet format
- **When** Nautilus engine needs market data
- **Then** bars are converted to proper Nautilus data feed format
- **And** all OHLCV data is preserved accurately

### Integration Requirements
**AC4**: Existing backtest job execution continues to work unchanged
- **Given** current `make backtest` command workflow
- **When** executed with new Nautilus engine
- **Then** job completes successfully with same CLI interface
- **And** no changes required to job orchestration

**AC5**: Integration with artifact persistence maintains current file structure
- **Given** backtest execution with new engine
- **When** artifacts are generated
- **Then** equity.parquet, orders.parquet, fills.parquet, metrics.json files created
- **And** file formats match existing schema exactly

**AC6**: BacktestRunnerPort interface pattern preserved
- **Given** services layer calling BacktestRunnerPort
- **When** using new Nautilus implementation
- **Then** method signatures remain identical
- **And** return values maintain same structure

### Quality Requirements
**AC7**: Integration tests verify Nautilus engine execution
- **Given** test suite for backtest runner
- **When** tests are executed
- **Then** tests verify real Nautilus engine is being used
- **And** stub calculations are no longer in execution path

**AC8**: Performance benchmark maintained (≤30s for 1-year AAPL backtest)
- **Given** baseline 1-year AAPL backtest
- **When** executed with new Nautilus engine
- **Then** completion time is ≤30 seconds
- **And** performance is equivalent to or better than stub

**AC9**: No regression in existing API endpoints or streaming functionality
- **Given** existing REST API and WebSocket streaming
- **When** backtests use new Nautilus engine
- **Then** all API responses maintain same format
- **And** streaming playback continues working unchanged

## Technical Implementation Notes

### Integration Approach
- Replace `NautilusBacktestRunner.run()` method implementation
- Preserve exact BacktestRunnerPort interface contract
- Use Nautilus Trader's backtesting engine with custom data adapter
- Maintain artifact generation in same format

### Data Conversion Strategy
```python
# Current: Polars DataFrame → stub calculations
# Target: Polars DataFrame → Nautilus DataEngine → Nautilus BacktestEngine
```

### Key Constraints
- **Interface Compatibility**: BacktestRunnerPort method signature unchanged
- **Artifact Format**: equity/orders/fills Parquet schema preserved
- **Performance**: Must not exceed 30s benchmark
- **Dependencies**: Minimal additional library dependencies

## Definition of Done
- [ ] Nautilus Trader engine properly integrated and executing backtests
- [ ] BacktestRunnerPort interface unchanged and working
- [ ] Artifact files generated in same format as stub implementation
- [ ] Integration tests pass with real Nautilus execution verification
- [ ] Performance benchmark met (≤30s for 1-year AAPL backtest)
- [ ] Existing API endpoints and streaming functionality regression tested
- [ ] Code follows existing adapter pattern in `backend/adapters/`
- [ ] Documentation updated with Nautilus integration details

## Risk Mitigation
- **Primary Risk**: Nautilus integration complexity breaking existing functionality
- **Mitigation**: Incremental implementation with feature flag for rollback to stub
- **Rollback Plan**: Environment variable `HEWSTON_USE_NAUTILUS_STUB=true` to revert
