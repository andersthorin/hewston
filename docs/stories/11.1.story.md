# Story 11.1 — Central Playback Clock, Timeline & Controls (v1)

Epic: E11 — Streaming Metrics & Synchronized Playback
Type: Feature
Status: Draft v0.1

## User Story
As a user, I want the playback UI to be driven by a single Playback Clock so that charts, metrics, orders, and the timeline remain synchronized during play, pause, and seek.

## Acceptance Criteria
- A central store provides: `currentSimTime (ISO)`, `playing`, `status`, `range {start,end}`
- WS/Worker ingester updates the store per frame
- Components (ChartOHLC, Metrics panel, Orders feed, Timeline) subscribe to the store
- Controls implemented: Play/Pause, Seek/Scrub (no speed control)
- Minimal timeline scrubber with event markers support (markers rendered from orders/fills in frames)
- Sync tolerance: components within one frame of the Playback Clock

## Notes & Constraints
- Maintain current OHLC behavior: hourly ticks, aggregated to daily bars (leverage existing ChartOHLC patterns)
- For finished runs, `range` is fixed; full scrub is available across the run window
- Use Context or a lightweight state library; preference is minimal dependencies

## Tasks
1) Define PlaybackClock store (Context or Zustand) with types and selectors
2) Refactor WS/Worker subscriber to dispatch frame updates to the store
3) Update ChartOHLC consumer to read from the store
4) Implement Timeline component with scrubber; render markers from frame orders
5) Wire Play/Pause/Seek to WS control messages through the store/controller
6) Add basic dev logging to verify sync

## Definition of Done
- Single source of truth enforced; no component keeps its own time
- Timeline scrubber works for finished runs; markers visible
- Controls operate through the store; chart/metrics/orders stay in sync


## QA Results

Decision: PASS (with conditions)
Reviewed by: Quinn (Test Architect)
Date: 2025-10-01

Summary
- Scope fit: Finished-run replay; centralized Playback Clock; Play/Pause + Seek/Scrub; timeline markers
- FE does not compute financial metrics; renders backend fields only
- Store design acceptable (Context + useSyncExternalStore) with selector-based subscriptions

Conditions to pass implementation gate
- Implement store contract as documented (selectors; imperative chart updates)
- Timeline scrubber: fixed range, accurate seek, markers aligned to orders
- Add unit tests for store transitions and selector stability; integration tests for one-frame sync tolerance
- Accessibility: basic keyboard/ARIA for scrubber (should-fix if time allows)

Risks
- Over-rendering at 30 FPS → mitigate via selector subscriptions and imperative chart API
- Marker density → cluster or compact rendering to avoid jank

NFR validation (advisory)
- Performance: Target 30 FPS; no visible jank; component renders bounded
- Reliability: Deterministic replay across two runs

Trace to acceptance criteria
- Single source of truth (store) → verified by design
- Controls and scrubber → test via integration
- Markers alignment → test via timestamp comparisons
